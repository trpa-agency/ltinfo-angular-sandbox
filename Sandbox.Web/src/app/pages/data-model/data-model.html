How Data Gets In

The rule. Every chart on the Monitoring Dashboard is an indicator in LT Info, linked to its monitoring program, and its numbers come from a map service layer: TRPA's or a partner agency's.

The exception. Transit ridership and the stormwater tools' load reductions are collected in LT Info, so LT Info is their source. Their charts read them live from LT Info through a named reader, not from a map service and not from a copy.

  1. Publish

    The data is a layer or table in a map service, on maps.trpa.org or on a partner agency's server.

  2. Register

    LT Info has an indicator for what is measured, with a definition and a unit, linked to its monitoring program.

  3. Bind

    The indicator names its layer, its axis, value, and series fields, and any filter. This is the proposed IndicatorDataSource record. An indicator on LT Info's own data names a native reader instead of a layer. A program names the layers for its site list and map the same way, in the proposed MonitoringProgramLayer.

  4. Chart

    The program page reads the layer through the binding each time it loads, so the chart is as current as the service.

Bind is proposed. LT Info has no tables for it yet, so no indicator or program is bound to a layer today. The numbers stay in the map service: LT Info stores the indicator and where to read it, not a copy of the values.

  • {{ t.linkedStored }}

    Indicators With Values Stored in LT Info

    {{ t.linkedStored }} linked indicators have values in LT Info and {{ t.linkedNoData }} have no data at all. The new LT Info API has no route that adds values; threshold updates save to draft tables only.

  • {{ t.plannedCharts }}

    Planned Charts, Read Live

    The redesign plans {{ t.plannedCharts }} charts. {{ t.chartsOnServices }} read a map service layer straight from the browser and {{ t.chartsOnFiles }} read an extracted file. None is tied to an indicator, and {{ t.programsToAdd }} of their programs are not in LT Info.

The Steps to Get There

  1. Register. Use the register below to agree on the indicator for each planned chart, then add the missing programs and indicators in LT Info. This needs no code.
  2. Bind. Add the IndicatorDataSource and MonitoringProgramLayer tables and a form to edit them. Program pages read the layer through the binding, and this page checks every binding against its service. Add the public native readers to the LT Info API for transit ridership and stormwater load reductions.
  3. Retire. Publish a service for each chart that reads a file. The nightly job that feeds the current dashboard stays as it is until cutover.

Tables

The indicator is the unit of record. On the left is what LT Info ingests on a schedule today. On the right are the two proposed tables. They are new, so nothing the current dashboard reads has to change.

IndicatorDataSource
One row per indicator, for a chart or a site's record over time: the service address and the layer, or the native reader for data LT Info collects itself, then the filter, the axis field (a date or a category), one or more value fields, the statistic to ask the service for, the series, pick, threshold, and site fields, the path it comes in by, the organization that owns the data, and how often the owner updates it. Rows are data that staff edit, not code. The Tahoe Yellow Cress Monitoring page already draws its charts from rows of this shape.
MonitoringProgramLayer
One row per layer a program page draws that is not a measurement: its site list, its sites per year, its map, and its map overlays. Each row has the service address, the layer, the filter, the name, year, and group fields, and the same path, owner, and update frequency. The Tahoe Yellow Cress Monitoring page already draws its sites from rows of this shape.
Columns and Settings
The fields every row of a kind reads are columns: the axis and value fields of a chart, the name, year, and group fields of a layer. How a row is drawn (chart type, labels, order, colors) is in one settings column on each table, ChartSettings and LayerSettings. A layer's other fields, such as a station code or the fields of a popup, are listed in LayerSettings too, and the check reads them from there.
What LT Info Does Not Store
A copy of the values. A page reads them from the service when it loads, so a chart is never out of date, and it shows a plain message when the service does not answer. Transit ridership and stormwater load reductions are already in LT Info because LT Info collects them; a native reader reads them where they are, the same way.
What Stays the Same
IndicatorReportedValue and the nightly monitoring ingest are untouched. Indicators that already hold values keep them.
